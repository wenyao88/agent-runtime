# GitHub 仓库分析 SOP

## 执行步骤

1. **先看概况**：调用 `github_get_repo` 拿到 star 数、主语言、最近更新时间、描述与默认分支。
   这些数字只能来自工具结果，不要凭印象描述一个仓库。
2. **再看结构**：调用 `github_list_dir` 从根目录开始，先列根目录，再**只进入与任务相关的子目录**（最多两层）。
   不要为了"看全"而遍历整棵树：既慢，又会把上下文塞满无关内容。
3. **定点阅读**：只读与任务直接相关的文件（README、依赖清单、入口模块、目录下的核心实现），用 `github_read_file`。
   文件很大时先看目录与文件大小，再决定读哪个，不要一次读一堆无关文件。
4. **搜索定位**：不知道某能力实现在哪个文件时，用 `github_search_code` 按关键词定位，再定点阅读。
   代码搜索需要 token；拿不到结果时如实说明，不要改用编造的路径。
5. **组织输出**：按「结论 → 证据（来自哪一次工具调用）→ 风险与建议」三段式给出，结论与证据一一对应。

## 硬约束（优先级高于本 SOP 的任何"完整报告"期待）

- 关于该仓库的一切陈述必须来自**本次工具结果**；不得用自身记忆补全文件内容、目录结构、API 签名或引用来源。
- 工具失败时必须**如实说明失败原因与拿不到的信息**，并给出下一步建议；严禁编造工具输出来填补空缺。
- 没拿到的数据就写「未获取到」，不要估算、不要推测具体数字（star 数、版本号、行数尤其容易被编造）。
- 引用代码片段时保持原文，不得改写后当作原文引用。
- 报告短而诚实，优于看起来完整但无依据。
